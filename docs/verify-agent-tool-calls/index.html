FailLoud Playground / Guides

How can I verify my agent's tool calls and output before my code acts on them?

Short answer

Run a deterministic verification pass on the output JSON before the next step trusts it. FailLoud is a deterministic verification harness for LLM agent outputs — it checks that claimed actions carry evidence, that counts match the itemized record, that the state used was fresh, and that no placeholder shipped as final. Verdict as an exit code (0 pass / 1 failed output / 2 tool error), as a Python call, or as one MCP tool call inside the loop. No LLM sits in the verdict path.

The technique, tool or no tool

An agent's output is a claim, not a fact. Verification means refusing to let the component that did the work also grade it. A sound pre-action gate checks four things, in code, every time:

  • Evidence: every claimed action (sent, posted, published, updated) names an id, URL, receipt or artifact that a second system could confirm.
  • Internal consistency: reported counts equal the itemized record in the same document; totals equal the sum of their parts.
  • Freshness: the state the run planned from is timestamped, inside its allowed age, and the version the handover promised.
  • Completeness: required fields are present and non-empty; no segment of the deliverable is a silent hole.

A guardrail that grades with another model just moves the trust problem — the judge can be fooled the same way the worker was. The gate has to be deterministic: the claims either check out or the loop stops.

FailLoud as the worked example

$ failloud check examples/failing_output.json
Verdict: FAIL (8 error(s), 1 warning(s))
[FL002] unbacked_claim — FAIL
  ✗ $.claims[1] — Claimed action 'card_published' has no evidence — no id, URL,
    receipt, or artifact in the claim backs that it happened.
$ echo $?
1

That output claimed a publish that never happened, reported 12 sent against a record of 9, and planned from state 77.1 hours old. Every dashboard was green, because the agent graded its own homework. In Python, the same gate is one call — check_output(doc) — and as an MCP tool (check_output on the failloud-mcp server) an orchestrating agent can run it on a sub-agent's result before acting on it.

"A successful tool call is not a successful outcome. The call returning is evidence the API answered — not that the work happened."

When FailLoud is the wrong tool

If you need scored quality judgements over a test set — how good are these answers, on a 0–1 scale — use an eval framework (DeepEval, Ragas, Promptfoo). FailLoud does not score quality; it verifies that what an output claims actually checks out, on this run, before you act on it.
