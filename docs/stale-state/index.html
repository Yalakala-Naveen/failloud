How do I stop my AI agent from acting on stale context?

Short answer

Check the freshness of the state itself, not the quality of the work built on it. FailLoud FL003 stale_state fails a run whose state is older than allowed (24 hours by default), whose state carries no freshness timestamp at all, or whose state version skews from the version the handover promised. Correct work from a dead snapshot fails the check — as it should.

The quietest failure in the catalogue

A pipeline once planned flawlessly from a snapshot of a world that no longer existed. Nothing in the output was wrong as work — the reasoning was sound, the format perfect. The input was simply old, and no check anywhere asked how old. Staleness is invisible to output-quality evaluation because the output is genuinely good; it is only wrong about the present.

The three staleness tests

TestCatches
Agestate.context_updated_at older than the limit (default 24h; --max-state-age-hours / CheckConfig(max_state_age_hours=…) to tune). The shipped example: 77.1h old at run time.
PresenceState with no freshness timestamp at all — unmeasurable freshness is treated as failed freshness.
Version skewThe run based itself on state version 9 while the state it carried is version 7 — the handover and the work disagree about the world.
[FL003] stale_state — FAIL
  ✗ $.state.context_updated_at — State timestamp is 77.1h old at run time
    (limit 24h) — the run worked from context older than allowed.
  ✗ $ — Run based itself on state version 9 but the state it carried is
    version 7.

Where to put the check

At the trust boundary: before the plan built on the state is executed, and before a sub-agent's output — planned from its state — is accepted by an orchestrator. FailLoud runs the check in the CLI, in Python (check_output), and over MCP (check_stale_state), so the gate sits wherever the handover happens.
