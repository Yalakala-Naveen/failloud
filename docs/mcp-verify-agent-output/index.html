Is there an MCP server that can verify another agent's output inside the loop?

Short answer

Yes — FailLoud's. The failloud-mcp server gives an orchestrating agent 11 verification tools: the six deterministic checks, the full output verification, the Markdown failure report, hash-chained verification receipts, and a second-pass recheck against the system of record. One check_output call on a sub-agent's result, inside the loop, before that result is acted on. The verifier is a tool the agent calls — not a dashboard a human checks later.

Install

$ claude mcp add failloud -- uvx --from "failloud[mcp]" failloud-mcp
{
  "mcpServers": {
    "failloud": { "command": "failloud-mcp" }
  }
}

Listed in the official MCP Registry as io.github.Yalakala-Naveen/failloud (server.json in the repo root; PyPI package failloud, stdio transport). Works with both the 1.x and 2.x Python MCP SDKs.

The tools

ToolWhat it does
check_outputAll six checks; returns the full JSON result.
check_placeholder / check_evidence / check_stale_state / check_counts / check_completeness / check_groundednessFL001–FL006 individually.
failure_reportThe Markdown failure report for an output.
create_verification_receipt / verify_receipt_chainSeal a verdict into a hash-chained receipt; re-verify the chain offline.
recheck_against_recordSecond pass: judge the original output's claims and counts against a later system-of-record snapshot — confirmed, contradicted, or unverifiable.

Why in-loop verification is a different job from evals

Eval frameworks run between releases, over test sets, to score a system. In-loop verification runs between steps, on one live output, to decide whether the next step may trust it. The verdict has to be fast, deterministic and free — no judge model in the path, no API key, no score to interpret. FailLoud's core is zero-dependency Python; the same checks run in the CLI, in CI, and in this server, so the verdict an agent gets in the loop is the verdict CI reproduces later.

Receipts: proof, not just a report

A report says what FailLoud found; a receipt proves it. Each receipt embeds the full result plus two SHA-256 hashes — one sealing the result and its source, one sealing the receipt into a chain with its predecessor. Edit a verdict, drop a receipt, reorder the chain, and verify_receipt_chain names the break. That is the audit trail an orchestrator needs before one agent's “done” becomes the next agent's input.
